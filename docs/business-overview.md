# Membership Communications Migration — Business Overview

For business analysts and the wider project team. Plain-language summary
of what this migration is, what's been done so far, what we've learned
from the real systems involved, and — most importantly — **what decisions
we need from the business to keep moving.**

## What this project is

ACSC sends members SMS texts, push notifications, and emails about
membership renewals, billing, and declined payments. Today, that's all
generated by 10 COBOL programs running on the mainframe, some of them over
a decade old. This project documents exactly how that system works today,
and designs its replacement on Salesforce Revenue Cloud — the platform
ACSC's Revenue Cloud implementation is already built on.

This is **not** a rip-and-replace. The same downstream delivery pipe (a
secure file-transfer system called MOVEit, very likely feeding into
Salesforce Marketing Cloud) stays in place. What changes is *where the data
comes from* and *what generates the file* — from mainframe COBOL reading a
1990s-era database, to Salesforce Apex reading the same Revenue Cloud data
your team already works in.

## How it works today

Each COBOL program does the same basic thing: look at members' renewal
dates, payment status, and billing plan; decide who's eligible for a
reminder; write a file listing those members; hand the file off to be
encrypted and delivered. Ten programs cover different situations —
different day-offsets before/after renewal, different payment states,
different channels (SMS, push, email).

| Program | What it sends |
|---|---|
| `MD021EX` | Renewal reminder, 13 days out |
| `MD022EX` / `ER` / `EC` / `LP` / `cc` / `ZA` | Family of renewal/payment-reminder variants — different day-offsets, campaign codes, payment states |
| `MD134ML` | Billing email for monthly-pay members |
| `MD572EM` | Card-decline email |
| `MD058CB` | EFT payment-method sync + notifications |
| `MD065CC` | Annual credit-card decline (identified, **not yet reviewed** — see Open Item 5) |

Full detail on every program: [`docs/cobol-legacy/`](cobol-legacy/README.md).

## Where the data actually goes (confirmed from real system configuration)

We got real screenshots of the file-transfer job configuration, not just
descriptions — this let us confirm, rather than guess, how delivery
actually works:

1. A file is written to a staging location.
2. A second, already-existing job encrypts it and sends it through MOVEit.
3. The encryption key is literally named for Salesforce (`salesforce-prod-042325-1`, "sfmc xfer") — strong evidence the file lands in **Salesforce Marketing Cloud**, not some other vendor.

See the diagram: [`docs/salesforce-design/source-to-destination-design.md`](salesforce-design/source-to-destination-design.md).

## What the target system looks like

We got a real, field-by-field audit of the actual Salesforce org — not
guesswork. That changed an early assumption: this migration targets
**native Salesforce Revenue Cloud** (standard Order/Asset/Account records),
not a separate CPQ/Billing add-on product as first assumed. Members are
represented as **Person Accounts**. Renewal, campaign, and billing-plan
data already has a real home in that org.

Full detail: [`docs/salesforce-design/high-level-design.md`](salesforce-design/high-level-design.md),
[`docs/salesforce-design/data-dictionary-reference.md`](salesforce-design/data-dictionary-reference.md).

## Work completed so far

- **All 10 COBOL programs documented** — what each one does, in plain terms, plus every past change and why it was made.
- **Real Salesforce org schema audited** — confirms the actual object model, not an assumed one.
- **Real delivery pipeline confirmed** — MOVEit job configuration, not guesswork.
- **Target design written** — how each legacy program maps to Salesforce objects and Apex code.
- **Starter Apex code written** — a scaffold, not production-ready, but a real starting point for developers, with every design assumption called out inline.
- **Workflow diagrams** for the four major flows (renewal reminders, billing email, card-decline, EFT sync).
- **Jira stories drafted**, ready to import, covering every phase of the work.

Everything above lives in this project's GitHub repository, organized under `docs/`.

## Decisions we need from the business / team

These are the open questions nothing above can answer on its own — each
one needs a person, not more analysis, to resolve:

1. **Who owns the file-transfer pipeline (MOVEit/AFT), and can Salesforce plug into it?** Salesforce can only make secure web calls — it can't write directly into the file share the mainframe uses today. We need 30 minutes with whoever administers MOVEit to confirm how Salesforce should hand off its files.
2. **Is Salesforce Marketing Cloud actually the final destination?** Strongly suggested by the evidence, not yet confirmed by whoever owns that system.
3. **Where does billing/payment data live?** No invoice or payment records showed up anywhere in the real Salesforce org audit. Renewal reminders and card-decline emails both depend on this — we can't finish those without knowing the answer.
4. **Should campaign-code rules actually be enforced going forward?** The real org already has a campaign-code system (`Campaign_Code__c`), but nothing currently enforces it. This migration would be the first thing that actually does — worth a conscious yes from the business, not an assumption.
5. **`MD065CC`'s source code is needed.** We found this program exists (via the team's own communications inventory) but never had its source to review — someone needs to track it down.
6. **Should card-decline emails still be split by state?** The legacy system produces 9 separate state files for card-decline emails. Was that a real requirement, or just how the mainframe happened to batch things? This changes how the new code is built either way.
7. **Correspondence logging scope**: should we log *every* billing email sent, or only the specific "letter 139" case the legacy code actually logs today (a 2025 change ticket implies the intent was broader, but the code never changed to match)?
8. **Is the old "flip bill plan back to manual" logic (in `MD058CB`) permanently retired**, or could it come back? It's currently disabled in production but still present in the code.
