Shared across every diagram — the flush() / MOVEit step

Every diagram below ends the same way: NotificationGatewayService.flush() uploads the run's extract file(s) toward the existing AFT/MOVEit delivery pipeline. The real Control-M/AFT job configuration shows this is two stages — a plaintext file lands in a staging drop point, then a Stage-2 job PGP-encrypts it and relays it via MOVEit. The PGP key is named for Salesforce Marketing Cloud (salesforce-prod-042325-1, "sfmc xfer"), and the real SMS extract uses SFMC MobileConnect-specific columns — strong evidence SFMC is the true final consumer, not MOVEit itself.

Confirmed: MOVEit itself is capable of PGP encryption, so Stage 2 may well be MOVEit's own automation. Still open: the exact endpoint, credential, and whether a new task needs provisioning for Salesforce-originated files — see high-level-design.md §4 and moveit-aft-reference.md before assuming a specific shape.

The legacy programs differ mainly in which gates apply and in what order — not the overall shape of the flow. Pushing those differences into Renewal_Notification_Rule__mdt lets one batch class serve all six programs (MD021EX, MD022EX, MD022ER, MD022EC, MD022LP, md022cc). MD022ZA is excluded because its eligibility logic lived entirely in an out-of-scope upstream job. The payment-in-transit gate (node E) remains genuinely unresolved, while the deliverability gate (F) and campaign-code gate (CAMP) are corrected to real, confirmed org fields.

03 Payment failure

Card-Decline / Dunning Flow (MD572EM)

sequenceDiagram
    participant PG as Payment Gateway
    participant PE as Card_Decline_Event__e
    participant H as CardDeclineDunningHandler
    participant EL as RenewalEligibilityRules
    participant NG as NotificationGatewayService
    participant CL as CorrespondenceLogger

    PG->>PE: Publish decline event
    PE->>H: Enqueue handler
    H->>EL: getClubRules(clubCode)
    H->>EL: getCurrentTermExpiration(asset)
    H->>EL: getYearsOfService(asset)
    H->>EL: getAmountDue(billingAccount)
    alt amount due is zero
        H->>CL: log Suppressed, AlreadyPaid
    else still autopay and unpaid
        H->>CL: log Skipped, RetryNextRun
    else eligible
        H->>EL: getMembershipNumber(asset)
        H->>EL: getUsableEmail(personAccount)
        alt no usable email
            H->>CL: log Skipped, NoEmail
        else usable email
            H->>NG: queueEmail(template, mergeFields)
            NG-->>H: queued
            H->>CL: log Sent, CardDecline
        end
    end
    H->>NG: flush()
    NG-->>H: upload result
    Note over H,CL: getProcessingDate() runs once at handler start

MD572EM's work-table-draining loop (fetch row, delete row, commit) has no direct Apex equivalent — Platform Events are consumed once, not left in a queue to retry. The "skip and retry next run" branch is modeled as a logged, no-op outcome; if true multi-day retry semantics are required, the recommended pattern is a scheduled batch re-query of whatever the org's confirmed payment/decline status source turns out to be after N days, rather than relying on Platform Event redelivery.

Each call maps to specific legacy logic: getClubRules replaces MD699BR, sourced from the working Asset.Club__c formula (not the broken CLUB_CODE__c). getCurrentTermExpiration replaces MD380MA via Asset.CurrentLifecycleEndDate — exact legacy match unconfirmed. getYearsOfService replaces MD642BR. getAmountDue replaces MD610BR and remains unresolved — no Billing/Payment object is confirmed anywhere in the org audit. getMembershipNumber is resolved — Asset.Member_Number__c, populated by the real RVNMembershipNo Apex (53% blank is a data-backfill gap, not an algorithm gap). getUsableEmail replaces MC501BCD, reading PersonEmail + Email_Status__pc on the Person Account directly, not a separate Contact. The final flush() hand-off mechanism is unresolved — see the shared note above the diagrams.

The historical "flip household bill plan back to AM and queue a printed letter" branch is intentionally omitted, matching its dormant/disabled state in current production (MEM-480905). MD058CB's mainframe checkpoint/restart and GO TO-based deadlock retry loop are replaced by Batch Apex's native per-scope transaction boundary and the job's natural re-runnability over Eft_Cau_Reject__c rows still marked unprocessed — a deliberate semantic change that should be validated against actual at-least-once/exactly-once processing requirements.
